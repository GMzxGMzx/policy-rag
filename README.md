# 工程政策合规问答（Policy RAG）

面向建筑与工程领域的政策问答系统：**条款级检索 · 引用可校验 · 证据不足直接拒答**。

可私有化部署，模型可切换（OpenAI 兼容协议 / 本地 Ollama）。

重心不在"调通大模型"，而在三件决定能不能上线的事：
**引用必须能反查、答不出必须拒答、失效条款必须提示。**

---

## 1. 项目定位

验证的命题：

> 政策问答里，错误答案的代价远高于没有答案。一个自信地引用了失效条款的系统，比一个说"查不到"的系统危险得多。

所以工程重心放在**可验证性**上：每条引用都会被反查，每个失败样本都会被归因，每次改动都能和基线对比。

---

## 2. 真实语料长什么样（这决定了一切）

用 13 份真实的住建/人社条线政策文件（江苏省、苏州市、徐州市）跑下来的实际情况：

| 情况 | 数量 | 占比 |
|---|---|---|
| 可直接抽文本 | 6 | 46% |
| **纯扫描件（需 OCR）** | **7** | **54%** |

能解析的 6 份，文体又完全不同：

| 文体 | 引用单位 | 例子 |
|---|---|---|
| 条例体 | 第X条 | 《建筑工人职业技能等级评价工作办法（试行）》38 条 8 章 |
| 通知体 | 一、二、三 小节 | 《苏州市建筑劳务企业动态核查工作通知》8 节 |
| 数字编号体 | 1. 2. 3. | 《徐住建发〔2023〕119号》5 项 |
| 附件/评分表 | 附件N | 动态核查评分标准（附件1-5）|
| 统计数据表 | 段落 | 《2021年度江苏建筑业发展报告》|

**这个分布直接推翻了一个想当然的设计**：只认「第X条」的解析器，在真实语料上只能救活 1/5 的可解析文件，其余全部退化成一整段。所以解析层必须同时支持三种结构。

---

## 3. 从真实语料里挖出来的七个坑

这一节是整个项目最有价值的部分——都是跑真数据才发现的，不是设计时能想到的。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 通知体文件变成一大段 | 只识别「第X条」 | 增加对「一、二、三」小节标题的识别 |
| 2 | 出现单条 **6417 字**的畸形条款 | 最后一个条款把后面 20 页附件全吞了 | 把「附件N」当硬边界 |
| 3 | 条款正文被切得支离破碎 | PDF 每行都带硬换行 | 按中英文规则做行回流 |
| 4 | 文档标题变成别人的文件名 | 取到了正文里「根据《XXX》要求」引用的文件 | 标题只在**第一个结构标记之前**找 |
| 5 | 「2021年度…报告」变成「年度…报告」 | 剥离序号的正则把年份也剥了 | 只剥 1–2 位短序号 |
| 6 | **引用有效率只有 0.33** | 引用解析只认「第X条」，通知体和附件的引用全被判无效 | 改为「拿上下文里真实存在的条号去回答里找」 |
| 7 | 红头文件的标题/机关识别错 | PDF 里标题没有语义标记（只是大字排版）| 引入人工校准清单 `data/raw/_meta.json` |
| 8 | 数字编号体被当成一整段 | 数字编号后面直接跟正文（不是「一、核查对象」那种短标题），按整行当标题会把正文切掉 | marker 只覆盖编号本身，正文从编号后开始；且仅在既无条号又无中文序号时才启用 |

第 6 条是最典型的：**改了一行解析逻辑，引用有效率从 0.33 跳到 1.00**。这种可量化的前后对比，比任何"我做过 RAG"的表述都有说服力。

## 4. 架构

```
政策文件 (.txt/.md/.pdf/.docx)
        │
        ▼
┌──────────────────────────────────────────────┐
│ ingest.py  解析 → 清洗 → 结构识别 → 条款切分   │
│  · 页眉页脚/页码剔除                          │
│  · 章-节-条 / 一、二、三 / 附件N 三种结构       │
│  · PDF 硬换行回流                             │
│  · 元数据：文号/机关/日期/施行日/废止清单       │
│  · 扫描件检测（抽不到文本必须显式报错）          │
└───────────────────┬──────────────────────────┘
                    │ Chunk（带上下文头）
                    ▼
        ┌───────────┴───────────┐
        ▼                       ▼
   BM25 倒排索引            向量索引
   （单字+二元+三元）      （BGE-M3 / OpenAI 兼容 / hash）
        └───────────┬───────────┘
                    ▼
              RRF 融合（k=60）
                    ▼
              Rerank（可选）
                    ▼
         上下文组装（最多 N 条，带引用头）
                    ▼
        LLM 生成（强制引用 + 拒答规则）
                    ▼
   引用反查校验 → 有效/编造分离 → 答案 + 引用
```

**引用校验发生在生成之后**：模型写出的每个 `【《文件》第X条】` 都和本次召回集比对，对不上记 `invalid_citations` 并判失败。于是"编条号"这个最常见的幻觉变成可度量、可回归的指标。

## 5. 快速开始

> **30 秒跑通（无需任何真实文件、无需 API key）**
>
> 仓库不含政策 PDF（体积大，且请以官方发布为准）。想立刻看效果，用 `data/samples/` 下的**虚构样例**：
>
> ```bash
> pip install numpy
> python -m scripts.ingest --raw data/samples --out data/index_sample
> python -m scripts.evaluate --index data/index_sample \
>     --cases data/samples/eval_sample.jsonl --out data/samples/runs
> ```
>
> 样例是虚构数据，只用于验证流程，不可引用。

### 先体检语料（强烈建议第一步）

```bash
pip install pypdf numpy
python -m scripts.inspect_corpus
```

会告诉你：哪些能解析、哪些是扫描件、哪些没有结构、有没有重复文件。
**在语料没搞清楚之前调检索，等于在沙子上盖楼。**

### 一、零依赖跑通（不需要任何 API key）

```bash
pip install fastapi uvicorn numpy httpx
python -m scripts.ingest
python -m scripts.evaluate
```

默认 `EMBED_PROVIDER=hash`、无 LLM：
- 向量通道用哈希词袋（**无语义**，仅供联调与基线）
- 生成降级为**抽取式**，直接返回命中条款原文

这条路径的意义：**检索质量可以被单独评测**，不会被模型润色掩盖。

### 二、接真模型

```bash
cp .env.example .env
# 填 LLM_API_KEY / EMBED_API_KEY，EMBED_PROVIDER 改为 openai
python -m scripts.ingest
python -m scripts.evaluate --tag with-llm
```

### 三、Docker

```bash
cp .env.example .env
docker compose up --build     # http://localhost:8000
docker compose --profile local up   # 完全离线（Ollama）
```

### 四、处理扫描件（7 份 / 13 份需要这一步）

> 逐份的找源方案（含已验证的官网链接）见 [`docs/扫描件补录清单.md`](docs/扫描件补录清单.md)。
> **优先找文字版，OCR 是最后手段。**

```bash
python -m scripts.export_images --only-scanned
# 输出到 data/ocr_pages/，逐页图片
```

然后用任一方式识别，把结果存成 `.txt` 放回 `data/raw/`：

- **白描 / 微信「提取文字」/ WPS** —— 最快，几十页够用
- **云 OCR**（阿里/腾讯/百度）—— 中文公文准确率最高
- **本地 PaddleOCR** —— 可离线，适合数据不出内网

> 更省事的办法：去发文单位网站找同一份文件的**网页版或 Word 版**，直接复制成 txt。
> 很多通知在网上都有 HTML 版，比 OCR 准确得多。**优先走这条路。**

导出工具不依赖 Pillow，直接处理 PDF 图像流的两种真实编码：
- `DCTDecode` / `JPXDecode` → 原始流就是 JPEG，直接落盘
- `FlateDecode` → zlib 解压出像素，用纯 Python 写 PNG

还有第三类会失败：**文字被转成矢量曲线的 PDF**（印刷稿常见），既没字体也没图片，
必须用渲染器（WPS「导出为图片」/ PyMuPDF）。工具会明确报出来，不会静悄悄漏掉。

## 7. 关键设计决策

| 决策 | 备选 | 为什么选这个 | 代价 |
|---|---|---|---|
| 三种结构切分 | 只认第X条 | 真实语料里条例体只占少数 | 解析器复杂度上升 |
| 附件当硬边界 | 按长度切 | 否则最后一条吞掉全部附件（实测 6417 字）| 附件内容独立成块，无章节归属 |
| 条款级切分 | 固定长度 | 引用必须精确到条 | 短条款信息量少，靠上下文头补 |
| PDF 行回流 | 原样保留 | 硬换行污染词频统计和引用显示 | 极少数排版会粘连 |
| BM25 + 向量 RRF | 只用向量 | 文号/条号类精确查询向量会失准 | 维护两套索引 |
| numpy 暴力检索 | Qdrant/pgvector | 万级数据约 5ms，少一个组件 | 超 10 万块需替换 |
| 引用后置校验 | 靠提示词约束 | 提示词不可靠，必须可验证 | 多一次解析 |
| 抽取式降级 | 没 key 就报错 | 让检索评测脱离生成独立可跑 | 降级模式无法拒答（见第 9 节）|
| 元数据人工校准 | 追求全自动 | 红头文件标题在 PDF 里无语义标记，自动必然出错 | 需要维护 `_meta.json` |

## 8. 评测体系

### 指标分三层，因为一个"准确率"无法定位问题

**检索层**：`Recall@k_文档`、`Recall@k_条款`、`MRR@k`（衡量排序，不只是有没有）
**决策层**：`应拒答_正确拒答率`、`可答_误拒答率`
**引用层**：`引用有效率`（能否在召回集反查到）、`要点命中率`

### Badcase 自动归因

| 类别 | 含义 | 该改哪里 |
|---|---|---|
| A | 该拒答却作答 | 拒答规则 / 检索阈值（最高优先级）|
| B | 检索未命中导致误拒答 | 切分 / 分词 / embedding |
| C | 召回到了却拒答 | 提示词过严 |
| D | 引用了不存在的条款 | 引用格式约束 |
| E | 答案对但条款没召回 | 运气命中，不可靠 |
| F | 要点覆盖不足 | 生成内容 |

### 回归对比

```bash
python -m scripts.evaluate --baseline data/eval/runs/20261110-133859.metrics.json --tag v2
```

报告出「本次 / 基线 / 变化」三列带 ↑↓，能一眼看出改动是改善还是恶化。

## 9. 当前实测结果

**语料**：13 份真实文件 → 6 份可解析 → 88 条 → 127 个检索块
**评测**：25 条样本（22 条可答 + 3 条应拒答）

| 指标 | 值 | 说明 |
|---|---|---|
| Recall@5 文档 | **1.00** | 22/22 命中正确文件 |
| Recall@5 条款 | **1.00** | 22/22 命中正确条款 |
| MRR@5 | **0.947** | 19 条排第 1，其余排 2~3 |
| 引用有效率 | **1.00** | 无编造引用（修复前是 0.33）|
| 要点命中率 | **1.00** | 抽取式直接摘原文 |
| 可答误拒答率 | 0.00 | |
| 应拒答正确拒答率 | **0.00** | ← 抽取式降级模式完全不会拒答 |

**必须坦白三点，否则这些数字会被面试官直接质疑：**

1. **127 个块、25 条样本的规模很小**，Recall=1.0 说明不了"效果好"，只说明**评测框架跑通了**。要谈效果，得在数百份文件、上万条款上重跑。
2. **embedding 用的是无语义的 hash 模式**。能拿到 1.0 主要是因为 BM25 在中文条款上本身很强 + 样本少。换成 BGE-M3 才可能在高难度口语化问法上体现差距。
3. **抽取式基线暴露了一个真结论**：检索全对，拒答率 0。说明"检索对 ≠ 系统可用"，LLM 在合规场景的价值主要不在润色，而在**判断该不该答**。这正是我做这个基线的目的——先证明必要性，再谈优化。

## 10. 已知局限

- **7/13 的语料是扫描件**，需 OCR 后才能用（导出工具已就绪，识别本身没做进代码；逐份找源方案见 `docs/扫描件补录清单.md`）
- 矢量描边（印刷稿）PDF 无法导出图片，需要外部渲染器
- 检索是 numpy 暴力计算，超 10 万块需换向量库
- 分词无词典，专业术语可能被切碎
- 引用只精确到条/节，不到「款」
- 附件内的表格（评分表）按文本处理，表格结构会丢
- **附录类附件会污染检索**：实测「附件」里有一页行政区划代码表（`006 铁门关市9007…`），
  它对任何业务问题都不相关，却因为长度和数字密度高而容易命中。
  这类附录应该在入库前排除，或按 `article_no` 做降权
- 单轮问答，无多轮指代消解
- 25 条评测集规模太小，指标波动大

## 12. 面试怎么讲（5 句话）

1. **为什么做**：政策问答错一个条款的代价远高于查不到，所以我把重心放在引用可校验和拒答，而不是生成效果。
2. **最难的地方**：不是 RAG，是**把真实政策文件切对**。13 份文件里 7 份是扫描件，能解析的 6 份里有 4 种完全不同的结构：条例体用「第X条」，通知体用「一、二、三」，还有用「1. 2. 3.」的，评分表用「附件N」。只认「第X条」的解析器只能救活一小半。
3. **怎么发现问题的**：我先做了语料体检工具，跑完才看到扫描件占一半以上、通知体占大头；又发现最后一条会吞掉 20 页附件，出现单条 6417 字的畸形条款。
4. **怎么证明改对了**：建了分层评测集，指标分检索/决策/引用三层，失败自动归因 6 类。比如引用解析只认「第X条」时，引用有效率只有 0.33；改成拿上下文条号反查后到 1.00。这种前后对比是可复现的。
5. **最有价值的发现**：抽取式基线检索全对但拒答率 0，说明"检索对 ≠ 系统可用"。LLM 在合规场景的价值主要不在润色，而在判断该不该答。

**如果被追问"127 个块也好意思说 Recall 1.0"**——承认。答：这个项目的产出是**评测框架和解析器**，不是效果数字；效果要等 OCR 补齐、真实语料上万条后重跑，我现在不会拿小样本的 1.0 说事。

## 13. 数据与合规

- `data/samples/` 下是虚构样例，不是真实政策
- `data/raw/` 下是公开政策文件
- **不要放入任职单位的内部文档**：涉及保密义务，也是面试风险点
- 系统输出不构成法律意见，需人工复核
